# AGENTS.md

## Design documents

The product design lives outside this repository, in the private `conao3/idea` repository. Read these before changing code:

- `projects/sanchoris/README.md`: the core value (predictable skills), terms, data, accounts, billing and plans, screens.
- `projects/sanchoris/skill.md`: predictable skills, nesting, user launch, threads, projects, triggers, the engine.
- `projects/sanchoris/architecture.md`: components and stack, data, boundaries, hosts and the driver, secrets, security and audit, build order, tests.
- `projects/design/sanchoris-flow/README.md`: the thread screen with the flow panel (design A).
- `projects/design/sanchoris-poc/README.md`: the other screens.

The previous implementation at `sancode-org/sanchoris-old` can be read for reference.

## Conventions

- Documentation, code comments, test names and commit messages are in English. User-facing text is written in English and translated through translation files.
- Stack: follow the shared new-project stack (`notes/new-project-stack.md`, `notes/lang/rust.md`, `notes/lang/typescript.md` in agents-share) and the section on components and stack in `projects/sanchoris/architecture.md`.
  - Rust (edition 2024) for the backend. Business logic, state transitions and input constraints are written in Lean, proved, and generated into Rust with leanfran (`conao3/lean-leanfran`). Every generated function called from Rust has at least one useful theorem, audited with leanassay (`#assay`).
  - TypeScript (Node 26, pnpm, vite-plus) for the UI with React 19, react-aria-components, Tailwind CSS v4 and lucide-react. Pure computations in the UI and the workspace agent are written in Lean and generated with the leanfran TypeScript backend, with theorems audited the same way.
  - Nix flake for everything; `make check` is the only verification entry point and runs the Rust checks and `vp run check`.
- Commit directly to `master` after the check command passes.

## Lean, Rust and TypeScript

- Lean owns business logic, state transitions and input constraints: types, specifications, implementations and theorems. The code lives in the Lake package `lean/` (package `sanchoris`, modules `Sanchoris.*`).
- `leanfran.toml` compiles the Lean modules with `leanfran generate` (leanfran 0.14.0). It has one `[[generate]]` table per destination, and each table lists its modules by name. A module goes to the crate or app that the table of what Lean covers in `projects/sanchoris/architecture.md` names: a Rust crate gets `crates/<crate>/src/generated` (module `crate::generated`), a TypeScript app gets `apps/<app>/src/generated`. A module that both languages call is listed in a Rust table and a TypeScript table. The generated code is committed and never edited by hand; `make check` regenerates it and fails on a diff or an untracked file.
- Rust owns input and output (HTTP, DynamoDB, S3, SQS, GitHub, Stripe, Firecracker) and the integration with crates, and calls the generated functions of its own crate.
- TypeScript owns the screens (`apps/frontend`) and the workspace program (`apps/sanchoris-agent`), and calls the generated modules of its own app for pure computations. The Thread channel between `sanchoris-agent` and the control plane is defined by `apps/sanchoris-agent/src/protocol.ts` and `apps/sanchoris-agent/PROTOCOL.md`, with an example of every message in `apps/sanchoris-agent/protocol/`; the control plane tests against the same examples.
- `sanchoris-config` checks the formats of the configuration files and the references to the outside in Rust, and the required keys, the references to States, reachability from `StartAt`, the terminal State and the place of `States.ALL` of a `skill.yaml` with `Sanchoris.SkillDefinition.validate`.
- `sanchoris-engine` runs `skill.yaml` with `Sanchoris.Engine`. `start` and `step` take the definition, the SkillRun, an event (the result of a command, a timer, `await`, `continue`, abort) and the time, and return the SkillRun with everything the transition writes: the StateEntries, the commands, the timers, the notifications and the outputs of `continue`. `waiterOf` and `parentOf` decide the parent of a new SkillRun. JSON values, paths, the intrinsic functions, Choice rules and RFC 3339 times are `Sanchoris.Engine.Json` and `Sanchoris.Engine.Expr`. Rust reads a validated `skill.yaml` into the Lean `Definition` (`crates/engine/src/definition.rs`), writes each transition as one `Transaction` of the async `Store`, keeps the result of a command by its idempotency key before the transition that takes it, writes the text of the notifications (`notice.rs`), and runs the `Command` States through the `Workspace` trait. The suites of `crates/engine/tests/suite/` run the skills against a Workspace that answers from a script, an agent that answers notifications, and a store that stops at each of its operations in turn; `crates/engine/tests/engine.rs` runs them on `MemoryStore`, and `crates/core/tests/engine_store.rs` on the DynamoDB store.
- `sanchoris-core` reads and writes DynamoDB and S3 (`docs/architecture.md` has the keys and the rules of the writes): the entities of a User under `U#<user>` with the unit of work `UserTx` (`db.rs`, `entities.rs`), the Plans of `infra/plans.json`, the store of the engine (`engine_store.rs`: one `TransactWriteItems` a transition, values over 32 KiB in S3), the outbox of the Thread channel, the thread-starter, the events, inputs and stop of threads (`thread.rs`), and Trigger evaluation (`trigger.rs`, with the event patterns of `pattern.rs`). The decisions of threads are `Sanchoris.Thread` (`step`, `deliver`, `decideStart`) and the place of a Workspace is `Sanchoris.Host.place`. Its tests run against DynamoDB Local: one server for each test process (`local.rs`), with a new User for each test.
- `sanchoris-worker` is the control plane's background work and the Thread channel (`docs/architecture.md`「Thread channel」): `channel` takes the messages of `sanchoris-agent` (`connect`, `receive`, `disconnect`, without state between calls), `deliver` sends the outbox in order and makes `start` and `credentials` when they are sent, `jobs` has the dispatcher's `route` and the jobs (thread-starter, restore, engine-worker, notifications, renewal of `credentials`), and `ports` puts the outside (connections, queue, scheduler, Workspaces, presigned URLs, GitHub) behind traits, with the local ones in `local`. `crates/worker/tests/channel.rs` runs every message of `apps/sanchoris-agent/protocol/` through the channel on DynamoDB Local.
- `sanchoris-graphql` is the schema of the screens; `apps/frontend/src/graphql/schema.graphql` is its contract, and `sdl_matches_the_contract` fails on a difference (`SANCHORIS_UPDATE_SDL=1 cargo test -p sanchoris-graphql` writes it). `sanchoris-api` serves GraphQL, the Thread channel's WebSocket and the local routes of the presigned URLs, and `sanchoris_api::local` runs the whole control plane in one process (`.env.example`).
- `step` of `Sanchoris.Thread` is one match on the event, each arm the equation of its theorem (`step_input`, `step_turnEnded`, …); `audit/Audit/ThreadStep.lean` audits it alone, and `audit/Audit/Thread.lean` names the theorems of `deliver` and `decideStart` with `using`, as `step` calls `deliver`.
- The theorems of the engine are in `Sanchoris.Engine.Theorems`, and `audit/Audit/Engine.lean` names them with `using`; `step` and `start` run on inputs of size 6. `await_returns_earlier_continue`, `continue_goes_to_waiting_await`, `run_timeout` and `retryDelay_le` are proved and not audited: random inputs rarely meet their hypotheses.
- `audit/` is a separate Lake package that requires `lean/` by path and leanassay by commit. `audit/Audit/<Module>.lean` has one `#assay` line per generated function that Rust or TypeScript calls, and one for each helper whose theorems state a property that the callers rely on. ## Commands

- `nix develop`: the development shell (Rust, Lean and Lake, leanfran, Node 26, pnpm, `vp`, DynamoDB Local).
- `make check`: the only verification entry point. It runs `nix fmt -- --ci`, `lake -d lean build --wfail`, `lake -d audit build --wfail`, `leanfran generate` with the diff and untracked check of the generated code, `cargo clippy --all-targets -- -D warnings`, `cargo test`, `vp run check` and `pnpm e2e`. The pre-commit hook and CI run it.
- `pnpm e2e`: the end-to-end tests of `e2e/`: the control plane on DynamoDB Local with local Workspaces (`sanchoris-agent` with the scripted fake Worker) and bare repositories in place of GitHub, driven through GraphQL.
- `make generate`: regenerate Rust and TypeScript from `lean/`.
- `make format`: `nix fmt` (Nix and Rust) and `vp fmt` (TypeScript).
- `nix run`: the control plane and the screens in one process on an in-memory DynamoDB Local, at `SANCHORIS_BIND_ADDR` (default `127.0.0.1:8080`), with one User on the Admin Plan. The settings of `.env.example` (a Config directory, Credentials, bare repositories, local Workspaces) pass through.
- `nix run .#driver`: `sanchoris-driver`.
- A change to `pnpm-lock.yaml` updates the `fetchPnpmDeps` hash in `flake.nix`.
- The type-aware lint of vite-plus runs the static musl build of tsrs: `pnpm-workspace.yaml` installs the musl packages and the `vp` wrapper of the flake sets `TSRS_BINARY`. The `vite` override in `pnpm-workspace.yaml` follows the `vite` dependency of the `vite-plus` version.
